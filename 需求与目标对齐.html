Token 消耗面板 · 需求与目标对齐

v2 已可运行 · 重新梳理目标与范围 · 2026-10-29
一句话定位
在额度耗尽之前告诉你，而不是耗尽之后才发现。

它不是监控工具（那是给运维看报表用的），是预警工具——目标只有一个：让你在写代码写到一半时，不要突然撞上 429。

所以判断功能该不该做，标准不是「能不能做」，而是「能不能帮你避免一次被打断」。

01为什么需要它

你的实际情况（今天实测）：订阅 MiniMax Coding Plan，双窗口限额，正在跑 Codex，消耗是持续的。

三个真实痛点，按严重程度排：

  • 撞墙时机不可控 —— 5 小时窗口滚动重置，你不知道它什么时候到期、还剩多少。写着写着突然不可用，上下文全断。
  • 消耗速度无感 —— 实测 2 分钟掉 8 个百分点。这种速度下，靠「偶尔想起来查一下」根本来不及反应。
  • 多供应商时更乱 —— 你有 20+ 个供应商配置，Codex 和 Claude 走的可能不是同一家，额度分散在几个后台里。
关键洞察：这个软件的价值不在「显示」，在「及时」。 如果它只是把网页后台的数字搬到托盘，那价值很有限——你还是得主动去看。真正的价值是它主动来找你：低于阈值时弹一次通知，或者图标变红让你余光扫到。

02目标分层

把目标拆成三层，避免一上来就想做全套。每层有明确的验收标准，达成即停，不超前。

已达成
L0
看得见
托盘常驻，一个数字说明当前额度。不用打开任何网页。
验收：余光扫一眼就知道还剩多少
L1
提前知道
低于阈值主动提醒；额度重置时告诉你恢复了。
验收：不需要盯着，它会在该提醒时提醒
L2
心里有数
消耗速率、还能撑多久、多供应商同屏、历史趋势。
验收：能据此决定「现在该不该开新任务」

当前在 L0 和 L1 之间。L1 是性价比最高的一步，L2 属于锦上添花。

P1 · 建议下一步做 性价比最高

功能为什么值得做成本
修 GDI 泄漏 当前内存 113 MB，每刷新一次漏一个 HICON 句柄，挂几周会耗尽 GDI。这是缺陷修复，不是新功能。 约 1 小时
阈值预警通知 L1 的核心。低于告急阈值弹一次 Windows 通知，额度重置时也提示。这是「预警工具」真正成立的地方。 约 2 小时
单实例保护 现在重复启动会出现两个托盘图标。用命名互斥量（Mutex）挡住第二次启动。 约 30 分钟
多供应商并存 不是「切换」，是同时看 2–3 家。托盘显示最紧张的那个，面板里分列。 约 3 小时

P2 · 可选，看你要不要 锦上添花

消耗速率预测按最近消耗速度算「还能撑 2.3 小时」。实现简单（记录两次采样求斜率），但要在 L1 之后才有意义。
历史趋势本地 SQLite 记录采样点，画 7 天曲线。能看出「我一周大概用多少」，但需要落盘和清理策略。
桌面悬浮条无边框 always-on-top 小条，可拖动。比托盘更显眼，但可能挡视线——你之前说过反感视觉干扰。
多机同步你有多台机器（配置是从 Mac 同步过来的），读 CC Switch 的 WebDAV 同步额度记录。

明确不做 范围边界

API 代理 / 转发那是 CC Switch 的职责，重复造轮子还会互相打架。
Key 管理 / 供应商切换同上，CC Switch 已经做得很好，硬要合并只会增加耦合。
Token 计费统计各家口径不同、缓存命中不算钱，算出来的金额不准，反而误导决策。
跨平台先只做 Windows。托盘和 DPAPI 都是平台绑定的，抽象成本不划算。
划这条线很重要。这个软件最容易失控的方向就是「顺手把 CC Switch 的功能也做了」——一旦开始管 Key 和切换，它就从「预警工具」变成「半个代理管理器」，复杂度翻十倍，而你真正需要的那个数字反而没人管了。

05技术路线：继续用还是迁移

维度PowerShell + WinForms（当前）Tauri v2
安装成本零（Windows 自带）需装 Rust 工具链，约 15 分钟
体积58 KB5–10 MB
内存113 MB（可优化到 70–80）40–60 MB
UI 上限低（自绘控件，做不了动画/图表）高（Web 技术，图表随便画）
迁移成本—约 1.5 天（重写数据层 + 界面）
适合场景L0–L1，自用L2，要图表/多供应商/给别人用
我的建议：先别迁。先花 1 小时把 GDI 泄漏修掉，看内存能压到多少。如果降到 80 MB 以下且你只需要 L1，PowerShell 版继续用完全够——它的 UI 上限确实低，但「托盘一个数字 + 弹个通知」这个需求，压根用不到 Web 技术。

真正该迁的信号只有一个：你开始想要 L2 的图表和趋势。那时候 WinForms 自绘曲线会让你痛苦，Tauri 的 1.5 天就值了。

07需要你拍板的四件事

Q1内存 113 MB 你能接受吗？
这决定要不要迁 Tauri。我的判断是先修泄漏看能不能压到 80 MB 以下，够用就别迁。
能接受，别折腾先修泄漏再看必须降到 60 MB，直接迁
Q2预警通知要什么形式？
「及时」是这个软件的核心价值，但提醒方式决定它会不会变成骚扰。
系统通知（Toast）图标变红就够，别弹窗托盘气泡提示都要
Q3你实际会同时用几家供应商？
如果只用 MiniMax 一家，S3「多供应商并存」可以直接砍掉，省 3 小时。
就一家两家（比如 MiniMax + DeepSeek）三家以上，要分列
Q4要不要历史趋势和速率预测？
这是 L2 的核心，也是唯一真正需要迁 Tauri 的理由。做它意味着加 SQLite、加图表、加清理策略。
要，值得先不做，以后再说只要「还能撑多久」，不要曲线
还有一个我必须提醒的风险：这些额度接口都是各家的未公开内部接口（MiniMax 的 coding_plan/remains、Claude 的 /api/oauth/usage、Codex 的 wham/usage），随时可能改字段、加签名、或者直接下线。这不是「会不会」的问题，是「什么时候」的问题。所以架构上必须做到：某个供应商失效时，其他供应商和整体界面不受影响，且能在配置页快速改地址自救。
